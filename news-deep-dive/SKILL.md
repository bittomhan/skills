# 行业新闻深挖（事件 + 主体）

适用场景：每日简报某条新闻被标记"值得深挖"，或用户说"深挖第 N 条 / 深挖 XX 事件 / 调研一下 XX 这笔交易"。

## 第零步：定位声明（强制第一步，写在成稿头部之前）

动手前先输出并锁定范围：

> **本次深挖对象 = 事件本身 + 各方主体。**
> 受众已知背景（监管框架回顾、自家项目影响分析、路线对比）**不进报告**——受众日常跟进已覆盖，至多结尾一句带过。
> 产出结构 = 终稿结构，不做"先写行业报告再审查精简"的返工。

2026-08-16 教训：RWA Global 交易深挖初稿带了完整的 42号文框架回顾 + 三条路线对比 + 对自家项目影响分析（占篇幅一半），被用户指出这些是"我们日常跟进很紧密的内容"，返工重做。**范围错位在第一步就注定返工，审查只能兜底。**

## 五步流程

### 1. 事件层（发生了什么）
- **一手时间锚点**：区分一手披露日（PR/公告/监管文件）与二轮传播日（媒体报道日），两者差几天很常见，成稿以一手日为准并标注二轮误传；
- **金额与条款性质**：区分绑定承诺 / 约数 / 纯意向（PR 原文措辞为准，如 "the figure is approximate"）；托管、赎回、审计等关键条款是否披露；
- **PR 话术 ↔ 事实落差翻译**：宣传定位翻成业务语言，列出从"签约"到"落地"之间的每道门槛。

### 2. 主体层（每一方是谁）
对事件涉及的每一方（甲方/乙方/中介/顾问）：
- 公司结构（注册地/控股/持牌辖区与牌照层级）；
- 团队背景（创始人/核心团队，自我介绍标注未独立核证）；
- **业务实质**：自我定位 vs 实际履历的落差（这是深挖最有价值的部分——如 "机构级顾问" 实为 launchpad 出身）；
- 可核实信息缺口 + 核实路径与成本（如商事登记调档、监管公示检索）。

### 3. 悬念层（什么决定走向）
- 列出决定事件成败/走向的未决问题（备案状态、资产真实性、对方资质）；
- 每个悬念给**验证时间戳与硬指标**（如"Q3 末复查""证监会备案公示可查"），能转成可执行观察项的不留成空泛"持续关注"。

### 4. 信源层（按可信度分级）
沿用三级信源体系（[高] 一手/官方 > [中] 行业媒体/律所解读 > [低] 未采信仅线索），利益相关方自述即使是一手也标注利益冲突。

### 5. 收尾（可选，≤1 句）
"对我们的意义"至多一句带过（如"观察哨：验证备案通道跨辖区可用"），不展开自家项目分析。

## 产出位置与命名（2026-08-16 Tom 确认）

- **位置**：与当日简报同目录（`推特Web3/每日简报/`），**不放主题子文件夹（如 RWA/）**——深挖源自当日简报条目，与简报放一起方便对照查看；
- **命名**：`YYYY-MM-DD [事件短名].md`（日期开头，与当日简报 `YYYY-MM-DD.md` 自然排在一起）；
- **不建任何子文件夹、不建「源文档/」**：深挖没有大量来源文件，平铺即可。此为「交付层文件夹规范」的**深挖类例外**（该规范仍适用于项目级交付，如 GT/嘉宝信）；
- **双版工作流平级进行**：底稿 `YYYY-MM-DD [事件短名].md` + 中间 `…（汇报版）.md` + 交付 `YYYY-MM-DD [事件短名].pdf` 三件同目录。

## 当日多事件合并（2026-08-16 Tom 确认，一天一个报告）

**同一天深挖 ≥2 条新闻时，并入同一个报告，不生成各自独立的深挖报告**——Tom 汇总一份转给俞总。

- **首事件**：正常产出 `YYYY-MM-DD [事件短名].md`；
- **当日新增第 2 个事件起**：并入同一文件（新增一章"事件 N"），文件重命名为 `YYYY-MM-DD [事件1短名]+[事件2短名].md`（日期后直接接事件名，**不加"深挖汇总"等字样**），PDF 同名重转；
- **多事件报告结构**：每个事件独立走完五步流程，按事件分章；顶部加一节「当日总览」（每事件一行结论）；信源清单合并去重放文末统一分级：
  ```
  # [事件1短名] + [事件2短名] 调研报告
  > 报告性质 | 调研时间 | 涉及当日简报条目：第 N、M 条

  ## 〇、当日总览（每事件一行核心判断）
  ## 一、事件 1：[名]（核心结论 / 事件基本盘 / 各方主体尽调 / 落地悬念）
  ## 二、事件 2：[名]（同结构）
  ## N、信源清单（合并，按可信度分级去重）
  ```
- 事件之间有关联（同一主体/同一监管动作）时，在总览中显式点出关联，不合并各事件的章节。

## 产出结构（= 终稿结构）

```
# [事件名] 深挖报告
> 报告性质 | 调研时间 | 关联项目（一行）

## 一、核心结论（3-5 条，只关于事件与主体）
## 二、事件基本盘（要素表：双方/时间地点/标的/金额性质/关键条款/核实状态）
## 三、各方主体尽调（每方一节：结构/团队/业务实质/缺口与核实路径）
## 四、落地悬念与待核实（悬念 + 验证时间戳/硬指标）
## 五、信源清单（按可信度分级）
```

篇幅目标 4-5 页 PDF；禁止出现的章节：监管框架回顾、路线对比矩阵、对自家项目的影响评估清单。

## 衔接

- **上游**：crypto-daily-briefing 简报条目可标【值得深挖】，由本 skill 承接；深挖报告引用简报条目编号建立溯源；
- **兜底**：research-report-review 审查此类报告时执行"受众适配"检查项（报告是否复述受众已知背景）；
- **输出**：对外交付走 md-to-pdf 双版工作流（底稿 md → 汇报版 md → 原名.pdf）；本 skill 产出结构即终稿结构，通常无需审查后再砍范围。

## 纪律

- 搜索收敛：每条关键事实至多 2 次检索，两独立来源一致即定稿；单源即标"单源·X 方披露·待核实"；
- 措辞不超证据：意向不写成协议、约数不写成承诺、推断标置信度；
- 底稿保留审计痕迹，对外 PDF 剥离（对接双版工作流）。
